# How Forge works

Forge is two things working together:

1. A small text protocol that an AI assistant can learn.
2. A local Python runtime that executes that protocol.

The assistant does not need direct filesystem or shell access to the machine
running Forge.

## The loop

    assistant writes bundle
            |
            v
    user runs bundle locally
            |
            v
    Forge parses and validates
            |
            v
    Forge executes locally
            |
            v
    Forge records a structured run
            |
            v
    Forge creates a canonical packet
            |
            v
    user returns packet to assistant

The packet closes the loop.

The assistant should reason from the returned packet, not merely from what it
intended the bundle to do.

## Structured run first

Forge execution produces a structured run containing information such as:

- run identity;
- status;
- parsed operations;
- operation results;
- errors;
- touched files;
- environment context;
- storage information.

The canonical packet is a deterministic text representation of that run.

## Packet and presentation are separate

The packet is the AI-facing audit trail.

Standard Forge prints that packet unchanged and then adds a very small human
summary.

A richer environment may present the structured run differently.

Presentation must not change the meaning of the canonical packet.

## Core and host are separate

Portable Forge receives resolved environment facts.

It does not discover platform details inside the core.

A standard terminal host might decide:

- current working directory is the project root;
- ~/.forge is the writable Forge home;
- stdin or a file provides bundle text;
- stdout receives the rendered result.

A Pythonista wrapper might instead decide:

- ~/Documents is the project root;
- clipboard provides bundle text;
- clipboard receives the result.

Both use the same Forge runtime.

## Why text?

Text is an interface almost every AI chat system already supports.

A Forge bundle can be:

- displayed;
- inspected before execution;
- copied;
- stored;
- reviewed;
- generated by different AI systems.

The runtime remains local.

This gives an AI useful local development capabilities without requiring the
AI provider itself to control the local machine.
